Dashboard — Backend Requirements

Everything the backend must expose to power the dashboard page (DashboardView.vue) with real data
Up to date
Updated July 3, 2026
Vue 3 + TypeScript frontend
~8 min read
ℹ️
Why this document exists

The dashboard is currently a working prototype: every number and card is hardcoded in the frontend (src/features/dashboard/), and the project has no HTTP client or env config yet. This spec tells the backend team exactly which endpoints, payload shapes, and business rules to build so the frontend can swap static values for live data.

01 What the dashboard page shows
Hero
HeroSection.vue — greeting + stat pillsNeeds the current date, the student's display name (greeting is hardcoded to "Student" and "Friday, June 12" today), and three counters: classes today, deadlines due this week, and overall completion %.
Schedule
ScheduleCard.vue — today's classesShows the class happening right now ("Live now" with a time range and a progress bar through the session) plus the next upcoming slot — or an empty state when nothing is left today.
Deadlines
DeadlinesCard.vue — nearest deadlinesLists assignments due soon: title, subject tag (e.g. "IT"), and a human-readable due label ("Due in 6 days") with a "Due soon" urgency badge.
Assignments
AssignmentsCard.vue — counters + quick taskShows three counters (Upcoming / Overdue / Done) and an interactive assignment row the student can tick complete directly from the dashboard.
Progress
ProgressCard.vue — completion donutA ring showing overall completion % plus a legend with On track / Behind / Done counts.
Groups
GroupActivityCard.vue — study group feedShows how many groups the student belongs to and recent activity (currently only an empty "groups are quiet" state exists).
02 Data contracts the frontend already expects
1
Dashboard counters — ProgressCounts
Defined in useDashboardProgress.ts. These five numbers drive the hero pills, the assignments card, and the progress donut. The backend should compute them server-side for the authenticated student.
TypeScript
export interface ProgressCounts { upcoming: number // not yet due, not completed overdue: number // past deadline, not completed done: number // completed assignments onTrack: number // in progress, pace >= expected behind: number // in progress, pace < expected }
2
Assignment shape — Assignment
The full assignments feature (src/features/assignments/types) already models this. The dashboard reuses a slimmed view of it, so deadline endpoints should return these fields — the frontend derives display labels like "Due in 6 days" itself.
TypeScript
export interface Assignment { id: number title: string subject: string // short tag, e.g. "IT" desc: string deadline: string // ISO date, yyyy-mm-dd progress: number // 0–100, derived from tasks completed: boolean invites: string[] // collaborator emails tasks: AssignmentTask[] }
3
Schedule event shape — ScheduleEvent
Defined in src/features/schedules/types. The dashboard's schedule card needs today's events of category class; the frontend decides which one is "Live now" by comparing start/end to the current time.
TypeScript
export interface ScheduleEvent { id: number title: string category: 'class' | 'study' | 'meeting' | 'exam' | 'personal' date: string // ISO date, yyyy-mm-dd start: string // 24h 'HH:MM' end: string // 24h 'HH:MM' location: string notes: string important: boolean reminderMinutes: number | null }
03 Endpoints to build
GET /api/v1/dashboard/summary Auth required (JWT)

Single aggregated call that powers the hero pills, the assignments counters, and the progress donut. Preferred over five separate calls — the dashboard renders all counters at once.

Response 200
{ "studentName": "Neath", "date": "2026-07-03", "classesToday": 1, "dueThisWeek": 1, "completionPct": 15, "counts": { "upcoming": 1, "overdue": 0, "done": 0, "onTrack": 0, "behind": 1 } }
GET /api/v1/schedules/today Auth required

Today's events for the schedule card, sorted by start. Return an empty array when there are no classes — the card has an empty state for that.

Response 200
[ { "id": 12, "title": "Software Engineering", "category": "class", "date": "2026-07-03", "start": "08:00", "end": "11:59", "location": "Room B2", "notes": "", "important": false, "reminderMinutes": 15 } ]
GET /api/v1/assignments?dueWithinDays=7&completed=false Auth required

Feeds the deadlines card and the quick-task row on the assignments card. Sorted by nearest deadline first. The frontend formats "Due in 6 days" from the ISO deadline — do not send pre-formatted labels.

Response 200
[ { "id": 4, "title": "My assignment", "subject": "IT", "deadline": "2026-07-09", "progress": 15, "completed": false } ]
PATCH /api/v1/assignments/{id}/completion Auth required

Backs the interactive checkbox on the assignments card (currently faked in useDashboardProgress.ts). Toggling must recalculate the summary counters, so the response returns them for an instant UI update.

Request
{ "completed": true }
Response 200
{ "id": 4, "completed": true, "progress": 100, "counts": { "upcoming": 0, "overdue": 0, "done": 1, "onTrack": 0, "behind": 0 }, "completionPct": 100 }
GET /api/v1/groups/activity?limit=5 Auth required

Recent activity across the student's study groups for the group-activity card. An empty items array triggers the "groups are quiet" empty state.

Response 200
{ "groupCount": 1, "items": [ { "id": 88, "groupId": 3, "groupName": "IT Squad", "actorName": "Dara", "type": "message", "summary": "posted in General", "createdAt": "2026-07-03T09:40:00Z" } ] }
04 Business rules the backend must own
Rule 1

Counter definitions must be consistent everywhere

The same numbers appear in three widgets, so compute them in one place. upcoming = not completed and deadline ≥ today. overdue = not completed and deadline < today. done = completed. onTrack/behind split the non-completed set by whether progress is keeping pace with time elapsed toward the deadline. completionPct = done ÷ total assignments, rounded to an integer (0 when the student has no assignments — never divide by zero).

Rule 2

Assignment progress is derived from tasks

When an assignment has tasks, progress = done tasks ÷ total tasks. Marking the whole assignment complete sets progress to 100 and completed to true. This mirrors the existing frontend behavior in the assignments store, so the dashboard checkbox and the assignments page never disagree.

Rule 3

Send raw dates and times, not display strings

Return ISO dates (yyyy-mm-dd) and 24-hour HH:MM times. The frontend already formats "Due in 6 days", "8:00 AM – 11:59 PM", and picks the "Live now" class locally — pre-formatted strings would break that and ignore the user's timezone.

Rule 4

Everything is scoped to the authenticated student

All dashboard endpoints derive the student from the auth token — no userId query params. Assignments shared via invites should count toward the invited student's dashboard too.

Java
// ✓ correct — resolve the student from the security context @GetMapping("/dashboard/summary") public DashboardSummary summary(@AuthenticationPrincipal StudentUser user) { return dashboardService.summaryFor(user.getId()); } // ✗ wrong — trusting a client-supplied id @GetMapping("/dashboard/summary") public DashboardSummary summary(@RequestParam Long userId) { ... }
Rule 5

"Due this week" and "classes today" use the student's local day

dueThisWeek counts non-completed assignments with a deadline within the next 7 days. classesToday counts today's events with category class. Accept an optional client timezone (header or query param) so "today" matches what the student sees.

⚠️
No HTTP client exists in the frontend yet

There is no axios/fetch layer, no .env, and no base URL configured. Once the backend publishes these endpoints (with CORS for the Vite dev origin), the frontend will add an API client and swap the stores over — so a stable contract matters more than an early ship date.

💡
Prefer one aggregate over many small calls

The dashboard renders six widgets on a single page load. /dashboard/summary plus the three list endpoints (schedule, deadlines, group activity) is the sweet spot — four parallel requests, each cacheable per student. Field names above match the frontend's existing TypeScript types exactly (camelCase), so keep the JSON casing as shown.

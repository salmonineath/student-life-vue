Schedules — Backend Requirements

Everything the backend must expose to power the calendar page (SchedulesView.vue) and event reminders with real data
Up to date
Updated July 3, 2026
Vue 3 + TypeScript frontend
~9 min read
ℹ️
Why this document exists

The schedules feature (src/features/schedules/) is fully functional today, but entirely client-side: the Pinia store seeds 10 demo events, persists everything in localStorage, and generates ids locally. An empty api/ folder is already scaffolded for the swap. This spec defines the CRUD endpoints, validation, and notification-scheduling responsibilities the backend must take over.

01 What the schedules page does
Calendar
TimeGrid.vue / MonthGrid.vue — month, week & day viewsRenders the student's events on a Google Calendar-style grid. View switching and date navigation are pure UI state — the backend only needs to serve the events for the visible date range.
Sidebar
ScheduleSidebar.vue — mini calendar, next event, week breakdownShows the next upcoming event and total minutes booked per category this week. Both are computed client-side in the store (upcoming, weekBreakdown) from the loaded events — no dedicated endpoints needed.
Event form
EventFormModal.vue — create / edit / deleteOne modal for the full lifecycle: title, category, date, start–end time, location, notes, important flag, and an optional single reminder (value + minutes/hours/days unit, stored as total minutes). Deleting asks for confirmation first.
Reminders
useEventReminders.ts — frontend-only reminder enginePolls every 30 seconds while the app is open and fires a toast + notification-center entry when an event enters its window (start − reminderMinutes). Fired reminders are deduped in localStorage. This only works while the tab is open — real scheduling belongs on the backend.
Briefing
SchedulesView.vue — on-load agenda toastsOn page load the view announces what's happening now, what's next today, important items, and the next future event. All derived client-side from the loaded events.
02 Data contract the frontend already expects
1
Event shape — ScheduleEvent
Defined in src/features/schedules/types. Every field below is already wired through the store, the calendar grids, and the form modal — JSON responses should match it exactly.
TypeScript
export interface ScheduleEvent { id: number title: string category: 'class' | 'study' | 'meeting' | 'exam' | 'personal' date: string // ISO date, yyyy-mm-dd (single day) start: string // 24h 'HH:MM' wall-clock end: string // 24h 'HH:MM', must be after start location: string // optional, '' when empty notes: string // optional, '' when empty important: boolean reminderMinutes: number | null // notify N min before start; null = off }
2
Create/update payload — ScheduleEventDraft
The form modal submits every field except id (Omit<ScheduleEvent, 'id'>). The same payload is used for both create and full update, so PUT semantics fit better than PATCH for edits.
TypeScript
export type ScheduleEventDraft = Omit<ScheduleEvent, 'id'>
ℹ️
Reminder is a single value in minutes

The form's "10 minutes / 2 hours / 1 day before" picker collapses to one integer (10, 120, 1440) before submit. The backend only ever sees reminderMinutes — never a value/unit pair. One reminder per event, matching Google Calendar's default row.

03 Endpoints to build
GET /api/v1/schedules?from=2026-06-29&to=2026-08-09 Auth required (JWT)

Events for a date range (inclusive), sorted by date then start. The frontend requests the visible month/week/day range on navigation instead of loading the student's entire history. The month view renders up to 6 weeks, so ranges can span two months.

Response 200
[ { "id": 5, "title": "Database midterm", "category": "exam", "date": "2026-07-01", "start": "09:30", "end": "11:00", "location": "Hall A", "notes": "", "important": true, "reminderMinutes": 30 } ]
POST /api/v1/schedules Auth required

Creates an event from a ScheduleEventDraft. The store currently invents ids with max+1 — the server must own id generation and return the full created event.

Request
{ "title": "Thesis advisor meeting", "category": "meeting", "date": "2026-07-06", "start": "14:00", "end": "14:45", "location": "", "notes": "", "important": true, "reminderMinutes": 15 }
Response 201
{ "id": 27, "title": "Thesis advisor meeting", ... }
PUT /api/v1/schedules/{id} Auth required

Full replace with a ScheduleEventDraft — the edit modal always submits every field. Returns the updated event. Changing date, start, or reminderMinutes must re-arm any pending reminder (see Rule 5).

PATCH /api/v1/schedules/{id}/importance Auth required

Backs the one-click importance toggle (toggleImportant in the store), used from the sidebar and event block without opening the full form.

Request
{ "important": true }
DELETE /api/v1/schedules/{id} Auth required

Permanent delete (the frontend already confirms with the user first). Return 204 on success, 404 if the event doesn't exist or belongs to another student. Any pending reminder for the event must be cancelled.

04 Business rules the backend must own
Rule 1

Re-validate everything the form validates

The modal enforces: non-empty title, end strictly after start (string comparison on HH:MM works because events are single-day), category one of the five enum values, and reminderMinutes either null or an integer ≥ 0. The backend must reject anything that violates these with a 400 — client validation is UX, not security.

Rule 2

Events are single-day, no recurrence — yet

The data model has one date per event and no repeat fields; a weekly lecture is currently stored as separate events. If the backend adds recurrence later, expose it as expanded per-day instances within the requested range so the existing frontend contract keeps working, and coordinate before adding an rrule-style field.

Rule 3

Times are wall-clock strings — store them as-is

date + start/end represent what's on the student's timetable ("class at 08:00"), not instants. Persist them verbatim (DATE + TIME columns, or strings) and never convert through UTC — a timezone round-trip would shift a 08:00 lecture to a different hour. Timezone only matters when the server computes reminder firing times (Rule 5).

Rule 4

Everything is scoped to the authenticated student

All endpoints derive the owner from the auth token; ids from other students return 404, not 403, to avoid leaking that an event exists. No userId parameters anywhere.

Java
// ✓ correct — ownership enforced in the query itself return repo.findByIdAndStudentId(id, user.getId()) .orElseThrow(NotFoundException::new); // ✗ wrong — fetch first, check later (or never) ScheduleEvent e = repo.findById(id).orElseThrow();
Rule 5

Take over reminder scheduling from the frontend

Today useEventReminders.ts polls every 30 s while the tab is open and dedupes fired reminders in localStorage under the key eventId|date|start|reminderMinutes — meaning a reminder re-arms whenever the time or offset changes. The backend should replicate exactly that: schedule a notification at start − reminderMinutes in the student's timezone, fire it at most once per (event, date, start, offset) tuple, cancel it on delete, and re-schedule it on edit. Delivery lands in the existing notification center (and later push/email). The frontend engine stays as an in-app fallback until this exists.

✅
The API slot is already scaffolded

src/features/schedules/api/ exists (empty, held by a .gitkeep). Once these endpoints are live, the frontend adds the client there and the store swaps its local mutations for API calls — no component changes needed.

💡
Serve by range, keep derived data on the client

One range query (from/to) covers every calendar view, the sidebar, the on-load briefing, and the dashboard's schedule card — sorting and per-week breakdowns are already computed client-side. Field names match the frontend's TypeScript types exactly (camelCase), so keep the JSON casing as shown. The one genuinely new backend capability this feature needs is server-side reminder scheduling.
